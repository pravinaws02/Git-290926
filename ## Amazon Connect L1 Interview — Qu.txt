### 3. How do you troubleshoot issues in Amazon Connect?

> “Usually, when I troubleshoot an Amazon Connect issue, I start with an actual affected contact. I take the contact ID and timestamp and first check the contact flow path to understand where the customer interaction failed.
>
> For example, if a healthcare customer says they entered their member ID but didn't receive their plan information, I check the Get Customer Input and Set Contact Attributes blocks to make sure the input was captured correctly. Then I check the Invoke Lambda block to see whether Lambda was successfully called.
>
> If Lambda is involved, I go to CloudWatch Logs and check the logs around the same timestamp. I look for timeout errors, exceptions, API failures or permission issues.
>
> I also check the CTR to understand what happened to that particular contact, and if required I correlate it with Splunk.
>
> If it's a routing issue, I check the queue, routing profile and contact attributes used for routing.
>
> Once I identify the root cause, I fix it in the lower environment, test the complete customer journey and then follow the change and deployment process for production.”

### 4. Why do you use API Gateway with Connect?

> “In our healthcare Amazon Connect use case, API Gateway can be used as the secure entry point for backend APIs when Amazon Connect needs to retrieve or submit customer information.
>
> For example, when a member enters their member ID in the IVR, the Connect flow invokes Lambda. Lambda can then call the API layer, which routes the request to the appropriate backend service. The backend returns information such as plan details or account status, and Lambda sends the required response back to Amazon Connect.
>
> So the flow is basically:
>
> **Amazon Connect → Lambda → API Gateway/API layer → Backend → Lambda → Amazon Connect**
>
> API Gateway provides a managed API layer where we can implement authentication, authorization, request validation, throttling and monitoring.
>
> If there is an issue, I would check the Connect flow first, then Lambda CloudWatch logs, and then the API layer to determine where the request is failing.”

### 5. How do you secure authentication in this flow?

> “We keep authentication as a separate step before allowing access to sensitive healthcare information.
>
> For example, when a member calls the Amazon Connect number, the IVR can ask for a member ID and another verification factor according to the business requirement. The information is passed securely to the backend through Lambda.
>
> Lambda validates the request with the backend authentication service. If authentication is successful, we continue the flow and provide the required information. If authentication fails, we don't expose member information and can either provide another attempt or transfer the customer to an agent.
>
> From the AWS side, we follow least-privilege IAM permissions, and sensitive customer information should not be written directly into CloudWatch logs. We mask or avoid sensitive values in logs.
>
> So the basic flow is:
>
> **Customer → Connect IVR → Authentication → Lambda → Secure API → Backend → Response → Connect.**”

### 6. API is returning 500 for many requests. Calls should not disconnect. What happens and how do you troubleshoot?

> “If the backend API starts returning 500 errors for many requests, my first priority is to make sure the customer call doesn't disconnect.
>
> I would design the contact flow with an error or fallback branch around the Lambda integration.
>
> For example, if a healthcare member calls and the IVR invokes Lambda to retrieve plan information, Lambda should handle the API failure properly instead of allowing an unhandled exception to terminate the flow.
>
> Lambda can return a controlled failure response to Connect. The flow can then play a message such as, ‘We're currently unable to retrieve your information. Please hold while we connect you to an agent,’ and transfer the customer to the appropriate queue.
>
> The flow becomes:
>
> **Connect → Lambda → API → 500 → Lambda handles error → Connect fallback → Queue → Agent**
>
> For troubleshooting, I would take an affected contact ID and timestamp, check the Lambda CloudWatch logs, confirm the 500 response, and check response time, exceptions and downstream failures.
>
> If an API gateway layer is involved, I would check its metrics and logs for increased 5XX errors, latency or throttling.
>
> I would also monitor Connect real-time metrics because a backend failure can cause more customers to be transferred to agents, resulting in a sudden queue increase.
>
> The key point is that an API failure should be handled gracefully rather than allowing it to disconnect the customer.”

### 7. DynamoDB has lots of product/service mappings. How exactly do you connect the IVR to the queue?

> “I would keep the product-to-service mapping in DynamoDB and use Lambda to make the routing decision.
>
> For example, suppose the customer selects Product A in the IVR. The Connect flow captures that selection as a contact attribute and passes it to Lambda.
>
> Lambda queries DynamoDB and gets the corresponding service and queue mapping.
>
> For example:
>
> **Product A → Technical Support → Technical Support Queue**
>
> Lambda returns the required routing information to Amazon Connect. The flow stores it as a contact attribute and then uses the appropriate Set Working Queue logic to route the customer.
>
> So the flow is:
>
> **Customer → Connect IVR → Product selection → Contact Attribute → Lambda → DynamoDB → Queue mapping → Set Working Queue → Queue → Agent**
>
> If there are hundreds of products, I wouldn't hard-code hundreds of conditions into the contact flow. I'd keep the mapping in DynamoDB and make Lambda reusable.
>
> For troubleshooting, I'd check the contact attributes, Lambda CloudWatch logs, DynamoDB response, Set Working Queue configuration and routing profile. Finally, I'd use CTR to verify the actual queue to which the contact was routed.”

### 8. What are Amazon Connect Security Profiles and IAM?

> “Security Profiles and IAM are two different layers of access control.
>
> An Amazon Connect Security Profile controls what a user can do inside the Amazon Connect instance. For example, an agent may have permission to handle contacts, while a supervisor may have additional reporting or management permissions.
>
> IAM controls access to AWS resources and APIs.
>
> For example, if Lambda needs to access DynamoDB, its IAM execution role can be given permission to access only the required DynamoDB table.
>
> So:
>
> **Security Profile → permissions inside Amazon Connect**
>
> **IAM → permissions to AWS services and resources**
>
> If an agent cannot perform something inside Connect, I would check the Security Profile. If Lambda cannot access DynamoDB or another AWS service, I would check the IAM role and policy.
>
> In both cases, I follow least privilege.”

### 9. How do you manage data in transit and at rest?

> “For data in transit, whenever information moves between Connect, Lambda, API services and backend systems, we use secure communication such as HTTPS/TLS.
>
> For example, when a healthcare member provides their member ID and Lambda communicates with the backend to retrieve plan information, the communication should be encrypted in transit.
>
> For data at rest, data stored in services such as S3, DynamoDB or databases should be encrypted using the appropriate AWS encryption mechanisms, with KMS where required.
>
> We also control access using IAM and resource policies.
>
> Another important part is logging. We should not put sensitive healthcare or member information directly into CloudWatch or application logs. Sensitive values should be masked or excluded.
>
> So:
>
> **In transit → TLS/HTTPS**
>
> **At rest → encryption + KMS where required + access control**
>
> And on top of that, we use least-privilege permissions and controlled logging.”

### 11. How do you authenticate GitHub to AWS?

> “For GitHub to AWS, I would use GitHub OIDC.
>
> In AWS IAM, I configure the GitHub OIDC identity provider and create a dedicated IAM deployment role.
>
> In the role's trust policy, I restrict access to our specific GitHub repository and approved branch.
>
> In GitHub Actions, I give the workflow permission to request an OIDC token and configure the AWS credentials action with the IAM role ARN.
>
> When the workflow runs, GitHub generates an OIDC token. AWS validates that token against the role's trust policy and provides temporary AWS credentials.
>
> So the flow is:
>
> **GitHub → OIDC → IAM Role → Temporary Credentials → AWS**
>
> We don't need to store permanent AWS access keys in the repository.”

### 13. How do you restrict a particular GitHub repository to an IAM role?

> “I restrict it through the **IAM role's trust policy**.
>
> For example, suppose the repository is:
>
> `mycompany/amazon-connect-project`
>
> In the role's trust relationship, I restrict the GitHub OIDC subject to that repository and branch.
>
> Conceptually:
>
> `repo:mycompany/amazon-connect-project:ref:refs/heads/main`
>
> I can also validate the OIDC audience as `sts.amazonaws.com`.
>
> This means another repository cannot assume that role unless it matches the trust-policy conditions.
>
> For production, I would normally have separate roles for Dev, Test and Prod and restrict each role appropriately.”

### 14. How do you call the IAM role from GitHub?

> “I call the AWS IAM role from the GitHub Actions workflow using the AWS credentials action.
>
> The important part of the workflow is:
>
> ```yaml
> permissions:
>   id-token: write
>   contents: read
>
> steps:
>   - uses: actions/checkout@v4
>
>   - name: Configure AWS credentials
>     uses: aws-actions/configure-aws-credentials@v4
>     with:
>       role-to-assume: arn:aws:iam::<account-id>:role/GitHub-Connect-Deploy-Role
>       aws-region: ap-south-1
> ```
>
> The `role-to-assume` contains the ARN of the IAM role.
>
> GitHub generates the OIDC token, AWS validates the trust policy and the workflow receives temporary credentials.
>
> I can also use `aws sts get-caller-identity` in the workflow to verify which role is being used.”

### 21. How long can Lambda run?

> “The maximum execution time for a single AWS Lambda invocation is **15 minutes**.
>
> But in my Amazon Connect use case, I wouldn't design the Lambda to run anywhere close to 15 minutes. It's mainly used for retrieving healthcare customer information from backend APIs, so I would keep the execution short and configure the timeout appropriately.
>
> If the backend is taking too long, I would investigate the API latency and Lambda CloudWatch logs rather than allowing the Connect interaction to wait for a long period.”

### 22. What happens if Lambda takes 20 minutes?

> “Lambda cannot run for 20 minutes as a single invocation because the maximum timeout is 15 minutes.
>
> If the execution reaches 15 minutes, Lambda terminates that invocation and it results in a timeout/failure.
>
> If this happened in our healthcare integration, I would check CloudWatch Logs to determine why the processing is taking so long.
>
> If the operation genuinely needs more than 15 minutes, I would redesign it as an asynchronous process using services such as SQS, Step Functions or ECS depending on the requirement.
>
> For Amazon Connect specifically, I wouldn't keep the customer waiting for that long. I would return a quick response or use a fallback path and, where appropriate, route the customer to an agent.”
